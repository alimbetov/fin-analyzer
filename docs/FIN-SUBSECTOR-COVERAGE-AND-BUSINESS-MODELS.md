## 2. Формальное определение достаточности

Отрасль не считается полноценно поддержанной только потому, что у неё есть три SF-формы. Полное покрытие считается по кортежу:

(юрисдикция, версия классификатора, код ОКЭД, подотрасль, модель получения дохода, стадия S0–S4, аналитическая цель, периодичность, методология).

**Обязательные уровни статуса:**
- CLASSIFIED — код/версия ОКЭД корректны; финансового вывода нет.
- GENERIC_ANALYSIS — доступны проверенные общие DF/F-показатели с явными ограничениями.
- SECTOR_DRAFT — выбран существующий SF-пакет и набор доп. данных; отраслевые формулы предварительные.
- METHOD_QUALIFIED — все необходимые формулы и контролируемые формы прошли независимое методическое ревью, golden/negative тесты и локализацию.
- UAT_ACCEPTED — реальный сквозной сценарий Excel/React → версии источников → расчёт → объяснение → решение → save/reopen подтверждён.
- REGULATED_REVIEW_REQUIRED — особая область (например, банковская/страховая, медицинская, бюджетная) требует отдельного разрешения экспертной методики; статус не подменяет предыдущие.

**Критерий полноты классификации:** каждый действующий код ОКЭД явно сопоставлен с одним или несколькими маршрутами: квалифицированный SectorPack / универсальный generic fallback / неприменимый или специализированный недоступный режим с причиной. Наличие generic fallback — не доказательство отраслевой диагностической достаточности.

### Критические методические границы

- **A:** IAS 41 при соответствующей базе МСФО: биологические активы не равны запасам на любой стадии; требования к оценке и раскрытию проверяются по применимому стандарту.
- **F/J/M:** признанная выручка, инвойс, контрактный backlog и полученные деньги различаются; IFRS 15 применяется к соответствующим договорам при МСФО.
- **K:** банк, страховщик, лизинговая компания и платежный оператор требуют отдельных методик. Страховые расчёты IFRS 17 нельзя заменить общим торговым P&L.
- **L/N:** аренда учитывается с учетом роли арендодателя/арендатора и применимого IFRS 16.
- **O/T/U:** это не типичные коммерческие ИП/ТОО; их нельзя автоматически включать в рейтинг «прибыльности бизнеса».
- **Q:** не собирать пациентов/диагнозы для экономических агрегатов, если можно работать без персональных медицинских данных.

Нормативная основа при применении МСФО: https://www.ifrs.org/issued-standards/list-of-standards/ias-41-agriculture/ ; https://www.ifrs.org/issued-standards/list-of-standards/ifrs-15-revenue-from-contracts-with-customers/ ; https://www.ifrs.org/issued-standards/list-of-standards/ifrs-16-leases/ ; https://www.ifrs.org/issued-standards/list-of-standards/ifrs-17-insurance-contracts/ .

## 4. Независимая ось бизнес-моделей

ОКЭД отвечает «что делает компания», а бизнес-модель — «откуда возникает доход и риск». У одной компании **может быть несколько моделей**, каждая привязана к сегменту или контракту.

| ModelCode (проектный) | Модель | Потребность в данных | Диагностика, которая должна быть доступна |
|---|---|---|---|
| BM-01 | Розничная перепродажа | SKU, цены, COGS, возвраты, запас | прибыль по SKU; stock days; markdown |
| BM-02 | Оптовая B2B торговля | дебиторка, лимит, условия платежа, клиент | gross margin, DSO, концентрация |
| BM-03 | Собственное производство на склад | BOM, партии, WIP, мощности | cost/unit, yield, запас готовой продукции |
| BM-04 | Производство под заказ | заказ, спецификация, этап, change order | margin per order, completion cash |
| BM-05 | Контрактная услуга | договор, часы, расходы, SLA | contract contribution, utilization |
| BM-06 | Разовая услуга/по записи | бронирование, исполнитель, материалы | contribution/job, slots |
| BM-07 | Проект/EPC | WBS, смета, акты, счета, платежи | estimate-at-completion, cash gap |

| BM-12 | Франчайзер | роялти, паушальный взнос, поддержка | royalty margin, network cohorts |
| BM-13 | Франчайзи | оборот точки, royalty, рекламный взнос | store EBITDA/cash after fees |
| BM-14 | Аренда недвижимости | договоры, ставка, занятость, расходы | NOI, vacancy, arrears |

| BM-16 | Перевозка/логистика | маршрут, машина, ton-km, топливо | contribution per route / empty-leg |
| BM-17 | Сезонное производство/агро | crop/season, фактические затраты, урожай | seasonal cash runway, yield |
| BM-18 | Лицензирование/IP/роялти | права, usage, royalty base, term | royalty accrual vs cash |
| BM-19 | Реклама и контент | аудитория, контракт, инвентарь, монетизация | yield per inventory unit, ad margin |
| BM-20 | Кредитование | loan book, ставки, риски, срок, резервы | margin and risk by vintage, regulated gate |
| BM-21 | Страхование | страховые договоры, премии, выплаты, обязательства | insurance service result, IFRS 17 gate |

## 5. Повторно используемые расширения форм вместо сотен новых бланков

К существующим 59 DF + 63 SF + 44 F/C/P/T/D рекомендуется добавлять только **типизированные расширения** (концептуальные семейства, не новые готовые formCode):

1. **XP-CONTRACT** — договор, обязательство, этап, признанный доход, акт, счёт, инкассация, удержание.
2. **XP-UNIT-ECONOMICS** — продукт/услуга, физический объём, net revenue, переменные и аллоцированные затраты, база распределения.
3. **XP-CAPACITY** — объект мощности, доступность, эксплуатация, простои, качество и натуральный знаменатель.
4. **XP-COHORT** — cohort, привлечение, удержание, переходы между тарифами, денежный поток по когорте.
5. **XP-ASSET-LEASE** — asset, право/договор, график, загрузка, обслуживание, CAPEX.
6. **XP-COMMODITY** — урожай/месторождение/партия, качество, товарный выход, хранение, цена, натуральные единицы.
7. **XP-GRANT-PROGRAM** — restricted funds, целевая программа, committed/received/spent и output.
8. **XP-REGULATED** — отраслевой режим, официальная методика, дата действия, лицензия/компетенция reviewer, ограничения отображения.

Правило **no duplicate form**: если поле с тем же смыслом, зернистостью, единицей и периодом уже есть в DF/SF, новая форма не создаётся. Если нужен другой смысл, присваивается новый стабильный код с версией и explicit mapping, а не переиспользуется старый. У каждого structured расширения один FormDefinition для React и контролируемого Excel.

## 6. Требования к SectorPack и применимости

Проектный контракт SectorPackDefinition:
- packId, packVersion, country, classificationName, classificationVersion, effectiveFrom/to;
- activityCodeRules — точные коды / утверждённые иерархические правила классификатора, не строковые эвристики;
- subsectorProfiles, supportedBusinessModels, stage S0–S4, supportedGoals, regulatedStatus;
- requiredDF, conditionalDF, selectedSF, extensionSchemas, documentEvidencePolicy;
- metricDefinitions(methodVersion, units, guards, precision, period, source evidence);
- questionGraph, nextBestQuestionRules, scenarioDefinitions, actionCatalog;
- cadencePolicyVersion, translations ru/kk/en, approval status and reviewer evidence.

Маршрутизация для смешанной компании: **BusinessUnit + EconomicActivity + BusinessModel + Contract/Asset/Product + Period**. Выручка, shared costs и долги по сегментам отражаются только при явной allocation policy; elimination нужна для группы; смешанная activity не означает автоматической двойной продажи.

Обязательные состояния ячейки/факта: PRESENT, EXPLICIT_ZERO, MISSING, NOT_APPLICABLE, ESTIMATED. ACTUAL и FORECAST не смешивать. Все денежные вычисления — exact decimal с provenance; агрегирование ratio по суммарным числителю/знаменателю, а не усреднению процентов.

## 7. Диагностический компас — одинаковый UX для любой отрасли

**Первый экран:** «Какой бизнес? (ОКЭД / список бизнес-моделей)» + «Что хотите решить?» + «Какие источники данных доступны?». Нет требования к заполнению 44+59+63 форм.

Для выбранной цели Engine строит **минимальный достаточный маршрут**:
1. 5–8 доступных агрегатов для предварительного S1 Business Check, если это методически допустимо;
2. от 1 до 3 отраслевых SF-форм для профильной диагностики + конкретные DF и применимые расширения;
3. более глубокие P/C/F-профили только при кредитной, инвестиционной, проектной или групповой цели;
4. результат всегда содержит: рассчитанные показатели; доказуемые сигналы; недоступные выводы; гипотезы; **один Next Best Question**; 1–3 сценария действий с допущениями;
5. настройку строгого отчёта с версией источников, методик, доступов и датой пересчёта.

**Пример торговля:** «какие товары замораживают деньги?» → SF-G01/G02 + DF stock/sales/cost → gross margin по SKU, stock days и aging → вопрос о фактической стоимости выбывших товаров → сценарий сокращения неликвидного запаса.

**Пример строительство:** «почему не хватает денежных средств при прибыльных объектах?» → SF-F01/F02/F03 + XP-CONTRACT → recognized/certified/invoiced/collected и прогноз cash gap → вопрос об удержаниях и сроке оплаты заказчика.

**Пример SaaS:** «почему выручка растёт, а денег меньше?» → SF-J01 + XP-COHORT + DF cash → MRR bridge, фактические collections, deferred revenue → вопрос об условиях предоплаты/помесячной оплаты.

**Пример банк/страхование:** без квалифицированной методики показывать только специально разрешённые management facts, completeness report и ограничения; не объявлять нормативную достаточность капитала или резервов.

## 8. Формальный план отраслевого тестирования

**CL-01:** загрузить официальную редакцию ОКЭД и проверить, что ни один действующий код не теряется и все mapping имеют источник/версию/дату. Изменение ОКЭД 2026 проверяется через переходные ключи.

**CL-02:** для каждой из 21 секции — минимум один golden case базового SF-набора, один негативный кейс и один кейс неприменимости (для O/T/U — некоммерческая трактовка).

**CL-03:** каждый подотраслевой профиль проверяет маршрутизацию к DF/SF/XP и явный gap, когда специализированная методика отсутствует.

**CL-04:** каждую из 26 моделей проверить на корректное признание дохода, расходов и cash; для агентской модели — GMV не выручка, для подписки — MRR не бухгалтерская выручка, для производства — закупка не COGS.

**CL-05:** отдельные golden cases для stock vs flow, 3/6/12 месяцев, сезона/когорты/проектного этапа, multi-currency, смешанной деятельности и IFRS-vs-management reconciliation.

**CL-06:** каждый квалифицируемый KPI имеет RU/KK/EN name/what/how/shows, definition of numerator/denominator, единицы, guard, period window, named methodology reviewer, fixture и provenance.

**CL-07:** по каждому приоритетному SectorPack — Excel download/upload round-trip, React parity, import preview, save/reopen, пересчет при новой ревизии, invalid-input, запрет незаметной потери данных.

**CL-08:** one-company-many-models E2E: смешанная торговля + сервис + подписка; ни одна продажа, возврат или общая статья не учитывается дважды.

**CL-09:** все regulated packs: управление доступом, minimization of sensitive data, regulator/jurisdiction/method version, restricted claims и экспертный gate.

**CL-10:** DecisionPacket содержит reproducible findings, формулу и source trace, missing-data list, one Next Best Question и сценарий действий; повторный прогон с тем же snapshot даёт тот же результат.

**Уровень приёмки:** SPECIFIED ≠ IMPLEMENTED ≠ METHOD_QUALIFIED ≠ UAT_ACCEPTED. Метрики покрытия публиковать отдельно: (a) 21/21 классификационных разделов; (b) mapping пятизначных ОКЭД; (c) число подотраслей с qualified packs; (d) число моделей с passed cases; (e) число реальных React/Excel UAT. Нельзя выдавать одну цифру «100% отраслей» за готовность всей системы.
