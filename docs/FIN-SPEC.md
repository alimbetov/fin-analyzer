# FIN Analyzer — мастер-ТЗ (FIN-SPEC v1.0)

**Статус:** DRAFT FOR IMPLEMENTATION · **Дата:** 2026-11-15 · **Репозиторий:** alimbetov/fin-analyzer  
**Техническая граница MVP:** полностью клиентское React-приложение; серверный Backend и БД **не требуются**.  
**Язык интерфейса MVP:** русский (архитектура готова к i18n).

## 1. Назначение

FIN Analyzer — профессиональное веб-приложение для контролируемого ввода, проверки, сравнительного анализа и визуализации финансовой отчётности компаний. Уникальность: версионируемые Excel-шаблоны отдельно для каждой формы, единственная каноническая финансовая модель, динамические настраиваемые стратегии, интерактивные графики и воспроизводимые заключения.

Основной пользователь: финансовый аналитик, консультант, финансовый директор, кредитный специалист или аналитик контрагента. В MVP — **индивидуальное использование локально**, без ролей, авторизации и совместной работы.

### 1.1 Основные цели

- Снизить ошибки переноса данных благодаря контролируемому формату XLSX и проверкам.
- Анализировать отчётность разных периодов без переписывания кода при изменении представления исходного документа.
- Позволить пользователю настраивать финансовые индикаторы, диагностические правила и шаблоны отчётов.
- Визуализировать результаты современными интерактивными диаграммами с точным происхождением каждого числа.
- Работать без отправки пользовательских финансовых данных на сервер.

### 1.2 Вне MVP

- Парсинг произвольных PDF и Excel с автоматическим утверждением данных; OCR/LLM как источник финансовых чисел.
- Сбор документов из ДФО, KASE и внешних источников; парсинг произвольных XBRL.
- Банковские и страховые специальные модели, инвестиционные рекомендации и нормативный кредитный скоринг.
- Достоверный прогноз дефолта/банкротства, ML-модели без проверенной исторической выборки.
- Многопользовательские права, централизованное хранение, синхронизация и цифровая юридическая подпись.
- Выполнение Quarto CLI внутри браузера; Quarto — возможный второй этап для внешней генерации публикационных отчётов.

## 2. Основной пользовательский путь (P0)

1. Открыть FIN в браузере (в том числе офлайн после подготовки статических ресурсов).
2. Создать локальный проект: компания, БИН (если есть), страна, отрасль, стандарт, валюта, тип отчётности (отдельная/консолидированная), отчётные периоды.
3. Для каждой финансовой формы **отдельно**: скачать шаблон XLSX или открыть эквивалентную React-форму.
4. Заполнить данные и импортировать XLSX обратно в соответствующую карточку отчёта.
5. Увидеть точный список ошибок: лист, ячейка, код показателя, правило, ожидание и фактическое значение.
6. Исправить файл либо данные в React; повторить проверку; подтвердить проверенные значения.
7. Выбрать стратегию анализа (комплексная / контрагент / кредитная / инвестиционная / управленческая).
8. Получить доступные коэффициенты, недостающие показатели, диагностические сигналы, графики и динамику.
9. Настроить состав интерактивного отчёта, экспортировать PDF / HTML / XLSX и сохранить локальный FIN-проект.
10. Позднее открыть файл FIN-проекта, восстановить данные и продолжить работу.

## 3. Отчётность и шаблоны

### FR-001. Отдельные карточки отчётов

MVP содержит:
- **Balance Sheet:** активы, обязательства, капитал.
- **Income Statement / P&L:** выручка, доходы, расходы, прибыль.
- **Cash Flow Statement:** потоки от операционной, инвестиционной и финансовой деятельности.
- **Statement of Changes in Equity:** движение компонентов капитала.

Пояснения/аудиторский отчёт — внешний первоисточник (метаданные/ссылка или локальная копия по усмотрению пользователя), без AI-извлечения. Финансовые организации — отдельная будущая модель.

Каждая карточка показывает: выбранные периоды, версию формы, последнюю загрузку, число ошибок/предупреждений, статус проверки, кнопки «Скачать шаблон», «Загрузить XLSX», «Редактировать в React», «Посмотреть значения».

### FR-002. Генерация шаблона

- Шаблон порождается из версионируемого FormDefinition + MetricRegistry, а не зашивается в Excel вручную.
- Включает листы конкретной формы, инструкцию, обязательные колонки, идентификатор формы, код каждого показателя, единицу и период; служебный лист _Metadata.
- Столбцы показателей позволяют ввод нескольких сопоставимых лет; редактируемые ячейки визуально выделяются, вычисляемые и технические — защищаются от случайной правки. Защита листа не является защитой от злоумышленника.
- Валидации Excel (типы/списки) служат подсказкой; **источник истины — проверки FIN после загрузки**.
- Генерируется шаблон именно выбранной формы (не один монолитный файл на все виды отчётности).
- Версия шаблона (schemaVersion/formVersion) обязательна; старые версии могут поддерживаться через явную миграцию. Неизвестные версии — отказ с объяснением.

### FR-003. Импорт XLSX

- Пользователь загружает только контролируемый XLSX от FIN; запрещены XLSM/макросы, внешние ссылки, исполняемые формулы как источник данных.
- Проверяются структура книги, технический манифест, коды показателей, дубликаты, типы, периоды, валюта, масштаб, количество листов и допустимые размеры.
- Финансовые значения считываются из ожидаемых ячеек; произвольные непредусмотренные листы/колонки не должны менять импортируемые данные.
- Excel-формулы и их кэшированные результаты **не считаются доверенным фактом**. Для ячеек ввода принимаются только разрешённые значения; формулы отклоняются с указанием ячейки.
- Импорт создаёт изолированный черновик (ImportSession), а не перезаписывает утверждённую ревизию.
- Повторная загрузка создаёт новую ревизию, доступно сравнение изменений и откат к ранее утверждённой ревизии.

### FR-004. React Financial Editor

- React-форма генерируется из той же FormDefinition, что и XLSX-шаблон; идентичные коды, обязательность и валидация.
- Доступны секции и иерархия строк, клавиатурный ввод, копирование/вставка числовых диапазонов, вид по годам, поиск и предупреждения рядом с полем.
- Запрещён незаметный автоперевод пустого поля в ноль.
- Пользователь может добавлять CustomMetric; такой показатель отдельно помечается пользовательским и не включается в стандартные расчёты без явного сопоставления/формулы.

## 4. Каноническая финансовая модель

### FR-005. Metric Registry

Для каждого показателя обязательны:
- устойчивый machine code (например TOTAL_ASSETS, CURRENT_ASSETS, TOTAL_LIABILITIES, TOTAL_EQUITY);
- название и описание, иерархия, тип stock/flow/ratio, категория;
- единица измерения, валюта/масштаб, знак и правила агрегирования;
- применимость к формам, отраслям, стандартам и версиям;
- допустимость ручного ввода либо расчёта по формуле.

В проекте хранятся Company, ReportingContext, Report, DocumentReference, MetricValue, MetricDefinition, FormDefinition, Revision, ValidationFinding, AnalysisRun, StrategyDefinition, ChartDefinition, ReportDefinition.

ReportingContext: отчётный период (начало/конец), дата окончания, годовой/промежуточный; basis = separate/consolidated; стандарт; валюта; масштаб. Значения из **разных** basis/валют/периодов не смешиваются без явного преобразования.

MetricValue: decimal-string (не JS number), показатель, период, контекст, происхождение (шаблон/лист/ячейка либо React), состояние подтверждения, revision ID. Missing/NotApplicable/Zero — три разных состояния. При экспорте JSON сохраняется исходная точность и масштаб.

## 5. Финансовая валидация

### FR-006. Правила проверки

**BLOCKER**:
- неподдерживаемый шаблон, неизвестные/дублирующиеся коды, недопустимая структура;
- ошибочный тип/значение или запрещённая формула;
- несогласованные компания/периоды/валюта/масштаб/консолидация;
- нарушение обязательных бухгалтерских тождеств, когда представлены все требуемые операнды;
- попытка подтвердить неполный набор обязательных полей выбранного профиля.

**WARNING / REVIEW**:
- нетипичное изменение значений, отрицательный капитал, отрицательный денежный поток;
- данные недоступны для части коэффициентов;
- ранее опубликованное число изменено; изменено определение метрики или формы;
- межформенные расхождения, требующие пояснений (без автоматического предположения о мошенничестве).

Контроли: активы = обязательства + капитал; арифметика промежуточных итогов; сверка начала/конца денежных средств с чистым изменением при наличии соответствующих данных; согласование чистой прибыли/движения капитала только с учётом раскрытых корректировок. Тесты должны исключать ложные блокировки при неполных исходных данных.

Статусы: DRAFT → VALIDATED → APPROVED (локальное подтверждение аналитиком). APPROVED — внутреннее действие приложения, **не** аудит, не юридическое заверение и не электронная подпись. Анализ официального типа строится только из утверждённой ревизии; черновые сценарии помечаются как предварительные.

## 6. Индикаторы и стратегии

### FR-007. Formula Engine

- Каталог начальных индикаторов: ликвидность, финансовая устойчивость, прибыльность, оборачиваемость, качество прибыли, денежные потоки, горизонтальный/вертикальный анализ.
- Формулы определяются безопасным типизированным DSL/AST: +-*/, SUM, AVG, LAG, сравнения; **запрещены eval, Function, произвольный JS/SQL**.
- Движок строит граф зависимостей и проверяет циклы, деление на ноль, отрицательные/нулевые знаменатели, сопоставимость контекста, типы stock vs flow.
- Примеры: CurrentRatio = CurrentAssets / CurrentLiabilities (при положительном знаменателе); NetMargin = NetProfit / Revenue (при положительной выручке); ROE = NetProfit / AverageEquity (при доступном положительном среднем капитале); FCF = OperatingCashFlow − CashCapEx (при надёжно установленном CapEx).
- При отсутствии входных данных результат = NOT_COMPUTABLE с перечнем недостающих метрик, а не 0/NaN.

### FR-008. Dynamic Strategy Builder

Встроенные стратегии MVP: FINANCIAL_HEALTH, COUNTERPARTY_RISK, CREDIT_SCREENING, INVESTMENT_ANALYSIS, MANAGEMENT_ANALYSIS.

Пользователь может создавать свою стратегию:
- цель, область применимости и отрасль;
- набор обязательных и дополнительных показателей;
- условные правила, пороги, приоритеты/серьёзность, текст диагностического сигнала;
- видимость графиков и разделов отчёта;
- политики нехватки данных и версии.

Порог риска — **конфигурация стратегии, а не универсальный финансовый норматив**. Нельзя выводить «кредит одобрен», «банкротство подтверждено», «инвестировать» на основании одних правил. Суммарный скоринг без калибровки не является обязательным для MVP.

Стратегия хранится и экспортируется как строго валидируемый JSON без исполняемого кода. Изменение стратегии не меняет утверждённые исходные данные.

### FR-009. Анализ и объяснимость

Доступны: тренды и темпы роста, структура баланса/расходов, ликвидность, рентабельность, долговая нагрузка, денежные потоки, качество прибыли, сценарный стресс-анализ и сравнение **сопоставимых** периодов/компаний.

Каждый результат показывает:
- точное значение, формулу и версию;
- входные показатели с периодами и ссылкой на конкретную исходную ячейку/поле;
- применённое правило и порог;
- ограничения, недостающие данные и предупреждения.

## 7. Графики и динамические отчёты

### FR-010. React Analysis Studio

Функциональные панели: KPI-cards, тренды, вертикальный/горизонтальный анализ, Waterfall, Treemap, Sankey (только если фактические потоки можно корректно агрегировать), Heatmap, комбинированные графики и таблицы.

Пользователь выбирает компанию/периоды/метрики/стратегию; все зависимые графики обновляются детерминированно. У каждого графика есть подписи единиц, масштаб, легенда, источник, объяснение, доступная табличная альтернатива. Цветовая индикация не подменяет текстовое объяснение риска.

### FR-011. Dynamic Report Builder

Разделы финансового заключения определяются конфигурацией (ReportDefinition): титул, резюме, показатели, тренды, качество данных, выявленные сигналы, методология и приложения. Пользователь включает/отключает разделы и меняет порядок.

Экспорт: печатный PDF, автономный HTML (статические срезы, а интерактивность — только при наличии автономных JS-ресурсов), XLSX аналитических таблиц. Экспорт фиксирует provenance, версии формул/стратегии, дату формирования и статус данных. Нельзя включать несчитанные или непроверенные значения как достоверные.

В MVP **не требуется Quarto**, но формируется нейтральный ReportSnapshot, пригодный для будущего внешнего Quarto renderer.

## 8. Сохранение и конфиденциальность

### FR-012. Local Project

- «Сохранить проект»: скачивание JSON (.fin.json) со схемой, версией, всеми согласованными контекстами, значениями, локальными стратегиями/настройками и историей ревизий; производные результаты могут пересчитываться.
- «Открыть проект»: валидировать версию/размер/структуру, безопасно импортировать, показать миграцию при необходимости.
- Сохранение без БД; необязательная локальная IndexedDB — отдельное решение после MVP, с понятным сроком хранения и предупреждением о возможной потере данных.
- По умолчанию **нет** внешних API-запросов, аналитических трекеров, загрузки документов в облако и выполнения сторонних скриптов из CDN.
- Не обещать шифрование «по умолчанию»: локальный файл доступен тому, кто получил к нему доступ. Защита файла паролем — отдельная функция.

## 9. Требования UX и NFR

- Современный React UI: светлая/тёмная темы, понятная иерархия, адаптация от desktop до планшета; основная работа рассчитана на desktop.
- Идентичная семантика финансовых форм в React и XLSX.
- Ошибки импорта должны иметь экспортируемый протокол.
- Доступность: клавиатурная навигация, контраст, подписи элементов, текстовые аналоги графиков (ориентир WCAG 2.2 AA).
- Производительность на эталонной desktop-конфигурации проверяется тестами: проект с 1 компанией, 10 периодами и 500 метриками должен оставаться интерактивным; прогон импорта/анализа и экспорта профилируется, целевые пороги уточняются по измерениям R0.
- Security: CSP, отсутствие eval, безопасное чтение XLSX/JSON, предельный размер, защита от zip bombs, формул и внешних ссылок, проверка значений и сериализации.
- Приложение можно статически разместить на GitHub Pages/любом HTTPS-хостинге; после загрузки активов не должно требовать API.

## 10. Бизнес-приёмка end-to-end

**E2E-01:** Создать компанию, скачать шаблон Balance за 2024–2025, заполнить, загрузить, получить корректные значения и статус VALIDATED.  
**E2E-02:** Нарушить равенство баланса на 1 единицу сверх разрешённой погрешности → точная ошибка, APPROVED запрещён.  
**E2E-03:** Попытаться загрузить XLSX с иной формой, формулой в поле, дублированным кодом, изменённым масштабом → безопасный отказ, утверждённая ревизия не меняется.  
**E2E-04:** Заполнить P&L в React, сравнить результаты с импортом идентичных данных через XLSX → полное совпадение.  
**E2E-05:** Отсутствует CashFlow → недоступные коэффициенты помечены NOT_COMPUTABLE, остальные рассчитаны.  
**E2E-06:** Создать правило риска и отобразить сигнал с формулой, источниками и значениями.  
**E2E-07:** Графики по 3 годам корректно отображают единицы/периоды; при смене стратегии перестраиваются без изменения фактов.  
**E2E-08:** Сохранить FIN-проект, закрыть/обновить страницу, открыть файл и воспроизвести результаты.  
**E2E-09:** Экспортировать PDF/HTML/XLSX и проверить совпадение значений, подписей, версий и предупреждений с Dashboard.  
**E2E-10:** В офлайн-режиме загрузить локальный шаблон, выполнить анализ и сохранить локальный проект (после первого кеширования приложения).

## 11. Приоритеты и границы поставки

**P0 / MVP:** шаблоны по формам, контролируемый импорт, React Editor, проверка, базовый Indicator Registry, 3 стратегии, 6–8 видов графиков, экспорт JSON/PDF, E2E.  
**P1:** расширенный Strategy Builder, сравнение компаний, расширенный Report Builder, HTML/XLSX аналитики, отраслевые профили.  
**P2:** Quarto CLI как опциональный внешний рендерер, XBRL, библиотеки эталонных наборов, расширенная отраслeвая аналитика.  
**Не включать без отдельного решения:** AI-импорт неструктурированных финансовых значений, облачное хранение и торговые/кредитные рекомендации.

## 12. Условия начала реализации

1. Согласовать словарь стартовых финансовых метрик и определение 4 шаблонов.
2. Зафиксировать формат Decimal/Missing, отчётные периоды, consolidation basis, валюты и шкалы.
3. Зафиксировать эталонные финансовые фикстуры (корректные и с намеренными ошибками).
4. Реализовать RED-тесты на парсер, валидацию и формулы до написания основного движка.
