# FIN DATA-CALC-R1 — работающие расчёты из введённых форм
## Техническое задание и поэтапный план доработок (UAT-first)

**Дата:** 2026-11-20  
**Версия:** 2.0 (переработка концепции расчётных приложений под текущее состояние репозитория)  
**Репозиторий:** alimbetov/fin-analyzer  
**Единственная целевая ветка:** feat/fin-form-library-standalone  
**Статус:** IMPLEMENTATION PLAN / NOT IMPLEMENTATION EVIDENCE  
**Главный приоритет:** корректный результат из заполненной и сохранённой пользователем формы.

## 1. Бизнес-цель и критерий результата

Пользователь FIN должен иметь возможность:

1. Открыть существующую финансовую форму в React.
2. Ввести или импортировать исходные значения, включая строки детальной формы.
3. Сохранить их как ревизию в fin_intake и повторно открыть без потери данных.
4. Нажать «Рассчитать», выбрав при необходимости метод и параметры.
5. Увидеть **числовые показатели**, дату/период, валюту, единицу, использованные источники, формулу и состояние полноты данных.
6. Исправить исходные данные, создать новую ревизию и получить новый воспроизводимый результат; старый расчёт остаётся связан с прежними исходными данными.

**Не считать задачу выполненной**, если есть только каталог форм, описание методики, SQL-функция на синтетическом наборе, зелёный unit-test, зарегистрированный contract SHA или открывающаяся вкладка без результата из сохранённой формы.

Цель первого выпуска — **F02 + C01/C02: подтверждённый путь React → fin_intake → UAT-расчёт → React**, с последующим развитием C05 → P04 → P09. Это не обещание расчётов всех 154 форм в первом релизе.

## 3. Архитектурное решение

### 3.1. Сохраняем 166 форм; добавляем вкладки, а не независимые отчёты

- Основной formCode остаётся прежним.
- «Расчётное приложение» — дочерняя вкладка/контракт/вариант вычисления, а не 167-я форма.
- Не создавать новые формы ради данных, уже присутствующих в DF-CSH, DF-STK, DF-AST, DF-SAL, DF-PRJ.
- Шесть CALC-A0X — **существующий реестр семейств**, использовать его повторно. Не создавать второй параллельный каталог с другим набором CALC-кодов.
- C07/F02 «признание выручки» пока **не входит автоматически в шесть реестровых семейств**; сначала использовать существующие расчёты F02 и типизированные источники продаж. Расширение реестра — отдельное обоснованное решение.

### 3.2. Единственный источник пользовательских значений — fin_intake

~~~text
React: форма / DF-детализация / расчётная вкладка
    ↓ ввод / paste / import
существующий canonical intake + save revision
    ↓
fin_intake: exact immutable revision (+ project, period, currency)
    ↓
FinIntakeUatSourceAdapter: read exact pinned revision / typed normalization
    ↓
existing UAT calculation pipeline (SQL/JDBC + Java BigDecimal)
    ↓
result + formula trace + source revision hashes + diagnostics
    ↓
React: числовые показатели, сверка, ошибка, повторный расчёт
~~~

**Не создавать третий writer.** Сначала исследовать и сблизить FormDraftService и ReportGridService; новые appendices — проекции/подчинённые сущности с общей семантикой ревизии и сохранения. Для event-строк использовать relational typed columns и business keys там, где это необходимо для расчётов.

**UAT не должен зависеть от независимого финансового S2.** Для введённых пользователем данных разрешён путь **FIN_INTAKE_UAT**, который читает строго зафиксированную ревизию и подготавливает канонический неизменяемый расчётный снимок. Он не записывает его в production fin_fact, не обходит существующие CHECK на production calc_plan и помечает результаты TEST_ONLY/UNQUALIFIED. Использовать существующие компоненты INGEST-2/CALC-4D там, где их интерфейсы пригодны; адаптер — интеграционный слой, не новый математический движок.

Если действующий калькулятор требует TEST_QUALIFIED synthetic FactSet, в первой итерации сделать ограниченный прототип **rev-to-UAT-source** и выбрать один путь по фактическим API/DDL. Запретить скрытую подмену сохранённых данных тестовыми seed-значениями. Для C01/C02 сохранять согласованное правило: дата среза берётся из version-pinned FactSet либо его UAT-эквивалента с явно зафиксированным asOf и provenance, а не из произвольного сегодняшнего времени или dueAt.

### 3.3. Расчёты — существующий общий движок

- PostgreSQL: фильтрация, grouping, SUM, latest AS_OF, проверка/соединение деловых ключей и batch arithmetic.
- JDBC: подготовленные запросы и типизированные результаты; без произвольного SQL из полей пользователя.
- Java 21 BigDecimal: бизнес-формулы, EIR/сценарии, округление по явной политике, контроль инвариантов, explainability.
- Существующие immutable MethodRevision/CalcPlan/UAT receipts использовать настолько, насколько они доступны. Новую plan-модель создавать только при доказанной несовместимости.
- Каждое выполнение прикреплено к точным входным ревизиям, версии метода и параметрам; при изменении источника новый результат строится отдельно.

## 4. Правила данных и расчёта

1. **PRESENT, MISSING, NOT_APPLICABLE, INVALID и числовой ноль** не взаимозаменяемы. Пустое поле не превращать в 0.
2. Деньги — PostgreSQL NUMERIC / Java BigDecimal. Не float/double для итогов. Не фиксировать новый глобальный scale и rounding без контракта.
3. Явно хранить исходную валюту; смешанную валюту нельзя суммировать без версии FX-конвертации.
4. AS_OF stock не суммировать по разным датам; period flows и YTD не суммировать повторно.
5. Нужны business key, дата события, ссылочная ревизия, stable row key и правила дедупликации; одного counterparty недостаточно.
6. Derived/output-only значения нельзя принимать от клиента как исходные финансовые поля.
7. Выводить не только число, но и единицы, период, исходные показатели, version/variant и причину отсутствия результата.
8. Для неверных данных возвращать понятный diagnostic с fieldCode/rowId, а не SQL stack trace в интерфейсе.
9. Если есть возможность рассчитать **часть** показателей корректно, вернуть их со статусом и показать отдельно заблокированные показатели; не фабриковать отсутствующие результаты.
10. Изменение presentation/языка/порядка колонок не меняет финансовый content SHA.
11. Добавление вкладки не должно менять идентичность исходной формы и существующих пользовательских ревизий.
12. Кандидатная финансовая формула в UAT должна явно иметь статус UNQUALIFIED; не запрещать её математический запуск из-за отсутствия S2.

## 5. Функциональный MVP — что должен увидеть пользователь

### 5.1. Первый сквозной результат: F02

Исходные поля из действующего F02: netRevenue, cogs, operatingExpenses.

Представить **уже существующие** кандидатные вычисления:
- grossProfit = netRevenue − cogs;
- grossMargin = grossProfit / netRevenue (при 0 denominator — UNDEFINED, не 0);
- operatingResult = grossProfit − operatingExpenses.

Данные берутся из реально сохранённой ревизии F02, а не из hardcoded fixture. Должен работать save → reload → calculate → change → recalculate. Сначала доказать точный повторный расчёт Java BigDecimal, затем SQL/Java parity из одного source snapshot. Не переименовывать существующие output codes без явной миграции соответствия.

### 5.2. Второй сквозной результат: C01/C02

Сначала реализовать **положительный AS_OF UAT snapshot**, уже поддержанный редакционной политикой V2. Это быстрый способ дать работающие показатели без преждевременного построения полноценного event-ledger:

| Форма | Обязательный UAT-выход | Дополнительный выход |
|---|---|---|
| C01 | netReceivables = SUM_AS_OF(gross) − SUM_AS_OF(allowance) | overdueGrossShare = SUM_AS_OF(overdue) / SUM_AS_OF(gross) |
| C02 | totalOutstanding = SUM_AS_OF(outstanding) | overdueOutstandingShare = SUM_AS_OF(overdue) / SUM_AS_OF(outstanding) |

C01: gross — остаток после платежей, **до** allowance. Overdue — часть gross, никогда не прибавлять отдельно. Allowance — положительный вычет. Cutoff — закреплённый AS_OF снимок.

C02: outstanding — непогашенные обязательства по подтверждённой snapshot-семантике; overdue — его часть. Для optional ratios полное отсутствие overdue, частично отсутствующие строки и нулевой знаменатель — разные состояния.

**Не заявлять**, будто эта первая версия уже восстанавливает историю платежей, автоматически оценивает ECL или корректно решает все бухгалтерские edge cases.

### 5.3. Следующая вертикаль: C05 → P04 → P09

После E2E F02/C01/C02 — поэтапно:
- C05: договор; датированные денежные выдачи/погашения; график долга; комиссии; ставка; изменение условий; досрочное погашение.
- P04: использует **тот же** источник графика, не хранит копию событий.
- P09: contract CFADS + cash debt service → DSCR; EIR для амортизированной стоимости **не подменяет** фактические денежные платежи.
- Параметры day count, fee treatment, rate basis, amortization schedule, rounding — версионируемые. Не применять универсальное EIR без датированных cash flows и явно выбранных конвенций.

### 5.4. Следующие направления (после работающего пилота)

| Формы | Имеющиеся источники | Минимально недостающие детали | Результат |
|---|---|---|---|
| C01/C02 расширение | DF-CSH-04/05 и DF-CSH-02 | связка payment ↔ obligation, аллокации, due-date changes | остатки, aging, объяснимая просрочка |
| C03 | DF-STK-02/03 | lot ID, ordered events, returns, units, NRV | FIFO / WAC / closing inventory |
| C04 | DF-AST-01 | service date, useful life, components, residual | depreciation roll-forward |
| C07/F02 | DF-SAL-01/03 | recognition date/basis, returns and variable consideration | признанная выручка и сверка |
| P07 | DF-PRJ-03/05 | датированные FCFF/FCFE, CAPEX, NWC, rate revision | DCF/NPV и sensitivity |
| P09 расширение | C05/P04 | versioned CFADS + matched cash debt service | DSCR по периодам |

**Правило:** если поле реально есть в существующей DF-форме, использовать его; если его нет — добавить дочерний типизированный контракт, а не новый независимый отчёт.

## 6. Расчётные приложения в UI

Первый интерфейс — **простой**, не 3D Atlas и не сложный методологический редактор:

- форма и стандартный редактор;
- вкладка «Расчёт» со списком показателей, кнопкой «Рассчитать», суммой, валютой, периодом;
- «Как получено» — формула, источники, ревизии и параметры;
- «Недостаточно данных» — конкретные недостающие поля / business keys и переход к источнику;
- «История» — два результата по двум ревизиям и сравнение;
- для C05 позднее: «Договор», «График», «EIR», «Досрочное», «Сверка P04».

React-компоненты рендерить по metadata и typed DTO; не зашивать новые финансовые формулы в TypeScript. Вычисление на backend. Не копировать сумму из результата обратно в source field.

Предварительный API-контракт (выверить и переиспользовать уже существующие контроллеры):
- GET /api/v1/forms/{formCode}/calculations — доступные выходы, методы, requiredness;
- POST /api/v1/uat/calculations/preview — pinned intakeRevisionId, formCode, variant/params → result + diagnostics;
- POST /api/v1/uat/calculations — commit immutable UAT result с idempotency key;
- GET /api/v1/uat/calculations/{id} — результат и lineage;
- GET /api/v1/uat/calculations/{id}/explain — пошаговое объяснение.

Ни один маршрут не считается существующим, пока это не установлено аудитом исходного API. Сначала адаптировать имеющиеся endpoints; новые вводить только при реальной необходимости.

## 7. План доработок (реальный порядок, а не формальный список)

### DC-R1.0 / P0 — Baseline и runnable smoke

**Задачи:** подтвердить HEAD; запустить backend + PostgreSQL 16 + React локально, пройти существующие F02/fin_intake smoke; проверить доступность SQL UAT pipeline и текущих API. Составить таблицу «возможность: код / тесты / реальный HTTP / браузер» с честными значениями PASS/FAIL/NOT_RUN.

**Выход:** docs/qa/FIN-DATA-CALC-R1-BASELINE.md с коммитом, командами, средой, результатами и 5–10 конкретными blockers. Нельзя считать прежние документы доказательством нового GREEN.

### DC-R1.1 / P0 — Pinned intake read и единый источник

**Задачи:**
- Проверить FormDraftService и ReportGridService, определить canonical revision/read adapter.
- Сформировать typed source snapshot, включая MONEY/DECIMAL/DATE/REF, rowId, contract version, period, currency, project и source SHA.
- Для F02 SINGLE_RECORD и C01/C02 ROWSET получать **те же значения**, которые показывает повторно открытый редактор.
- Устранить различие ключевых полей сохранения без массового переписывания legacy.
- Выполнить негативные тесты missing/duplicate/stale revision.

**Приёмка:** GET read-back по точному ID ревизии даёт идентичные нормализованные значения после рестарта PostgreSQL; изменение истории не переписывает предыдущий снимок.

### DC-R1.2 / P0 — UAT calculation bridge

**Задачи:** соединить typed snapshot с существующим execution pipeline, повторно использовать UAT CalcPlan/SQL/JDBC/Java, записать snapshot identity + hashes в результат, не трогая production admission. Реализовать bounded calculation input и явную несовместимость source types.

**Приёмка:** два запуска на одной ревизии/методе/параметрах детерминированы; запрос с другой ревизией создаёт отличимое lineage; SQL и Java дают одинаковые expected values там, где предусмотрен dual-run.

### DC-R1.3 / P0 — F02 из реально сохранённой формы

**Задачи:** подключить три существующих показателя F02 к React и UAT; save/reopen/calculate/change/recalculate, объяснение grossMargin и zero denominator.

**Приёмка:** полный браузерный E2E с минимум двумя ревизиями, BigDecimal и PostgreSQL read-back. Без искусственной подстановки seed-значений.

### DC-R1.4 / P0 — C01/C02 из сохранённых ROWSET

**Задачи:** использовать существующие AS_OF формулы, политику V2 и UAT-результаты миграции 050; связать точные ревизии C01/C02 через typed intake adapter, поддержать несколько строк, полноту optional input, одну валюту и дату среза.

**Приёмка:** по 2–3 строкам исходной формы видны netReceivables/totalOutstanding и необязательные доли; обновление одной строки не меняет исходный старый расчёт; overdue не складывается с gross/outstanding.

### DC-R1.5 / P0 — Generic Calculate/Explain React

**Задачи:** вкладка расчётов, отображение источников/периода/единиц/значений, предупреждения о неполноте, кнопка повторного расчёта и история результатов. Универсально для F02/C01/C02.

**Приёмка:** Playwright: выбрать задачу → форма → изменить поле → сохранить → рассчитать → показать происхождение → открыть ревизию → сравнить результаты.

### DC-R1.6 / P1 — CALC-A01: ledger-based allocation

**Задачи:** добавить только действительно отсутствующие business obligation key, payment key, allocation, amendment и cancellation events поверх DF-CSH-02/04/05; не создавать дубли invoice или списаний.

**Приёмка:** один долг + 2 частичных оплаты + изменение dueAt + корректировка → корректные остаток, overdue и aging; повтор оплаты не удваивает результат.

### DC-R1.7 / P1 — CALC-A05: C05/P04/P09

**Задачи:** один реальный для UAT пример кредита, typed расписание и события, отдельно contractual cash и EIR, P04/P09 с тем же источником, отсутствующий CFADS — typed diagnostic.

**Приёмка:** полный сценарий выдачи, регулярных платежей, комиссии, досрочного погашения, графика и DSCR; Excel/ручная контрольная таблица сравнивается с Java и SQL.

### DC-R1.8 / P1 — C03, C04, C07/F02, P07

**Задачи:** по одному репрезентативному договору/активу/SKU/сценарию с реальным вводом и расчётом, затем расширение по бизнес-вариантам. Перед новыми операторами проверять готовые функции и выражения.

**Приёмка:** для каждого семейства — собственный golden dataset, браузерный путь и source lineage.

### DC-R1.9 / P2 — масштабирование на 154 числовые формы

Вести **матрицу по выходам**, не по числу React-экранов. Для каждого output: код формы, формула, исходные поля, статус источника, метод, вариант, тест, реальный intake E2E. 12 EVIDENCE форм участвуют как документы/основания, но не обязаны производить арифметические показатели.

Не объявлять все 154 формы просчитанными на основании наличия семейств CALC-A01...A06.

## 9. Проверки, без которых «работает» не засчитывать

Минимальные тесты для F02, C01, C02 и затем каждого нового семейства:

1. Сохранение → чтение → идентичные данные после restart.
2. Числовой golden example с независимым ожидаемым результатом.
3. Missing vs 0; zero denominator → undefined (не 0).
4. Отрицательные значения/некорректные знаки согласно выбранному UAT-профилю.
5. Два периода или две ревизии не смешиваются.
6. Разные валюты не суммируются без явного FX.
7. Дубликат business key/rowId не даёт двойную сумму.
8. Формула и версия параметров восстановимы из результата.
9. SQL/JDBC и Java BigDecimal parity, когда оба пути реализованы.
10. React browser E2E на реальном backend и PostgreSQL, без mocked numeric response.
11. Повторная команда/ошибка в середине операции не создают дубли.
12. Старое сохранённое значение и старый результат не переписываются новой редакцией.

Для PostgreSQL использовать PostgreSQL 16/Testcontainers либо локальный compose. H2 unit tests **не заменяют** доказательство реального SQL/DDL. Нагрузочные p95/p99 для каталога и массовых расчётов — после functional GO; на этапе R1 не блокировать демонстрацию из-за отсутствия 5k/10k нагрузочного прогона.

## 10. Что сознательно НЕ делаем сейчас

**Отложено до отдельного этапа:**
- Keycloak/OIDC, полноценные роли, production IAM, ABAC/RLS-hardening как отдельная программа.
- Платежи/подписки, расшаривание проектов, публичный доступ.
- Создание нового HTAP-хранилища, Redis/Caffeine для расчётных значений, Kubernetes.
- Дополнительные security moderation/revocation flows поверх необходимых тестовых guardrails.
- Независимая финансовая S2-квалификация каждой методики как предварительное условие запуска тестового расчёта.
- Массовая разработка 154 математических реализаций без первичного входного E2E.
- Переработка UI в Atlas/3D до работающей таблицы «ввод → расчёт → результат».

**Но не отключать элементарную корректность:** параметры SQL, проверка типов, границы количества строк, изоляция localhost для прототипа, отсутствие write в production и защита от потери ревизий обязательны. Отложенная безопасность не разрешает вводить очевидные ошибки данных.

## 11. Принципы последующего расширения

1. Сначала максимально использовать DF-CSH/DF-STK/DF-AST/DF-SAL/DF-PRJ и поля основных форм.
2. Новое приложение создавать только для **недостающей детализации** (платёжное распределение, партия, компонент актива, признание выручки, сценарий, датированный график).
3. Контракты дочерних вкладок дополняют форму, а не создают независимый источник тех же сумм.
4. CALC-A0X остаётся семейством варианта/методики. UI-приложений и финансовых выходов может быть больше; их не надо искусственно приравнивать 1:1 к шести семействам.
5. Финансовые параметры (ставки, методы, валюты, интервалы, пороги) всегда фиксируются в версии расчёта; UAT может применять явно помеченные рабочие допущения.
6. Документация и автоматические coverage-счётчики должны отличать: REGISTERED, MATH_TESTED, UAT_EXECUTABLE, INTAKE_E2E_PASS и FINANCIALLY_QUALIFIED.

## 12. Definition of Done и артефакты

**Для первого выпуска R1 (F02 + C01/C02):**
- Работают локальные PostgreSQL, backend и React.
- F02 сохраняется/открывается и возвращает 3 вычисленных значения из своей введённой ревизии.
- C01 и C02 сохраняются/открываются в ROWSET и возвращают определённые UAT snapshot-показатели.
- Любой показанный результат ссылается на точную форму/ревизию/период/валюту/версию формулы; нет захардкоженных входных сумм.
- Missing, zero denominator, несовместимая валюта и устаревшая ревизия отображаются как typed diagnostics.
- Есть обязательные PostgreSQL integration и Playwright E2E; тестовый отчёт привязан к HEAD SHA.
- Не изменены идентичности 166 форм и исторические миграции.
- Нет ложного заявления о S2 и нет production publication.

**Обязательные артефакты реализации:**
- docs/qa/FIN-DATA-CALC-R1-BASELINE.md (факты и запуск);
- docs/FIN-DATA-CALC-R1-SOURCE-TO-OUTPUT-MATRIX.tsv (source → field → output → formula → readiness);
- backend/controller/service diff + новые additive migrations только по необходимости;
- React Calculate/Explain view;
- golden vectors + PostgreSQL tests + Playwright E2E;
- docs/qa/FIN-DATA-CALC-R1-ACCEPTANCE.md (PASS/FAIL/NOT_RUN и SHA).

**Суть приёмки:** пользователь вводит финансовые данные и видит объяснимый, воспроизводимый финансовый расчёт. Все остальные архитектурные и организационные задачи подчинены этому результату.
