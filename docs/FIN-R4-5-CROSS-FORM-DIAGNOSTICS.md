# FIN-R4.5 — Межформенная комплексная финансовая диагностика

**Состояние:** SYNTHETIC PILOT IMPLEMENTED (backend only); **method S2:** pending; **production ACTUAL:** HOLD; **Keycloak/ABAC + React E2E:** not implemented.  
**Branch:** `feat/fin-r0-r1a`; `main` не изменять.

## 1. Целевое изменение

Диагностика FIN должна работать не в границах отдельной Excel-формы, а по **графу верифицированных экономических фактов** за один согласованный период и связанную дату предыдущего закрытия. Любой исходный показатель (`MetricCode, MethodVersion, BusinessScope, Period, ReportingBasis, Currency, FactSetRevision`) является вершиной графа. Рёбра — **утверждённые**, методически типизированные отношения между показателями; сходство названий не создаёт финансовую взаимосвязь.

Не путать:
- `ACCOUNTING_IDENTITY`: проверяемое математическое бухгалтерское тождество, с нулевым остатком.
- `CROSS_REPORT_RECONCILIATION`: сверка отчётных потоков и остатков; при различиях не подменять результат и фиксировать отсутствующие внешние корректировки.
- `ECONOMIC_BRIDGE`: экономическая декомпозиция, не утверждает причинность.
- `QUALITATIVE_PATTERN`: совместный сигнал нескольких показателей, гипотеза без причинного доказательства.
- `STATISTICAL_ASSOCIATION` (будущий этап): требует подходящего длинного ряда, контроля тренда/сезонности/множественных проверок и раздельного статуса исследования; **не является** тождеством или причинностью.

Проверять отношения только при **одинаковых** entity/scope, учётной базе, валюте, конкретной версии опубликованных фактов и при выверенных периодах. **Потоки** относятся к `[start, end)` отчётного месяца, **остатки** — к точной дате конца месяца; `prior closing stock` относится к концу предыдущего месяца, а не суммируется с потоками.

## 2. Реализованный граф-пилот (6 правил)

| Правило | Входы | Статус результата | Обязательная оговорка |
|---|---|---|---|
| BALANCE_IDENTITY | F01: ASSETS, LIABILITIES, EQUITY | RECONCILED/DEVIATION | Согласованная политика отражения баланса |
| CASH_ROLLFORWARD | F01 CASH_END(t-1), CASH_END(t); F03 CFO/CFI/CFF(t) | RECONCILED/DEVIATION | FX, состав денежных эквивалентов и реклассификации пока не моделируются |
| CASH_LEDGER_CASHFLOW_BRIDGE | DF-CSH-01 CASH_IN; DF-CSH-02 CASH_OUT; F03 CFO/CFI/CFF | REVIEW, numeric difference | Нельзя приравнивать банковские поступления к отчётным потокам без сверки охвата |
| OPERATING_RESULT_TO_CFO | F02 REV_NET/COGS/OPEX; F03 CFO | OBSERVATION | Simplified operating result != net income; gap != доказанная причина |
| RECEIVABLES_CASH_STRESS | F01 AR_END(t-1/t), F02 REV_NET, F03 CFO | REVIEW/OBSERVATION | Рост AR и отрицательный CFO — гипотеза для проверки, не доказательство задержки платежей |
| GROSS_MARGIN | F02 REV_NET/COGS | OBSERVATION/NOT_COMPUTABLE | При нулевой/отрицательной выручке маржа не рассчитывается автоматически |

Для любого отсутствующего обязательного показателя правило возвращает `MISSING_EVIDENCE` и список конкретных `MetricKey + TimeRole`. Никаких `MISSING -> ZERO`, `OBSERVATION -> CAUSE`, `HYPOTHESIS -> CONFIRMED`. Правило с числовым исходом содержит точные `SourceRevision + FormCode + Field + RowId + FactId`.

## 3. Исполняемые компоненты

- `CrossFormDiagnosticEngine.java`: детерминированный расчёт на BigDecimal и фиксированный versioned rule graph, 6 отдельных методик с явными статусами.
- `TrustedCrossFormDiagnosticService.java`: читает только опубликованный `SYNTHETIC` FactSet из PostgreSQL. Для каждого выбранного входа проверяет `FIN-PILOT-V1`, соответствие каноническому metric code/version/time kind, происхождение source row, документный hash vs immutable population control и `TrustedFinancialPopulationService.requireComplete`. Блокирует смешанные валюты, неправильные даты stock/flow, чужие источники, двойные итоговые значения, неопределённую версию, несколько source revisions для одного metric/time и неподтверждённые суммы.
- `CrossFormEvidencePlanner.java`: только **один шаг** по утверждённым рёбрам от уже доступных фактов; предлагает **недостающие** F01/F02/F03/DF-CSH-01/DF-CSH-02, группирует по форме, объясняет разблокируемые правила и нужный период, не предлагает все 166 форм.
- Межформенный `assessAndPublish` сохраняет snapshot в существующей неизменяемой `fin_diag.assessment_run` под `CROSS_FORM_PILOT`, включая исходные доказательства, числовые результаты, незакрытые зависимости и `nextEvidencePlan`. Повторный расчёт на одном fact-set/method-version идемпотентен, при дрейфе чисел/определения возвращает отказ. Исторические снимки не переписываются; `loadPublished` помечает устаревшую редакцию фактов.

**Важно:** как и в старой `TrustedBusinessDiagnosticService`, caller-provided `authorizedOrg` — пока только server-side placeholder. Нет OIDC/ABAC HTTP endpoint, поэтому новый сервис не экспонируется клиенту. Текущий production ACTUAL запрещён.

## 4. Финансовый путь пользователя

1. Выбор проблемы: например, «продажи растут, денег меньше».
2. Берём **все** пригодные утверждённые факты на дату и период в одном FactSet, а не только форму F02.
3. По графу методик определяем требуемые показатели и связанные F01, F03, DF-CSH. Если есть — переиспользуем; если нет — показываем конкретные источники с месяцем/полем и статусом необходимости.
4. Проверяем общий финансовый результат и связанные остатки, сверяем денежные потоки, измеряем расхождение, выделяем гипотезы по дебиторке.
5. Выводим карточку находки: числовая формула, период, происхождение исходных цифр, статус качества, оставшиеся вопросы, какие данные способны разрешить гипотезу. Совокупная диагностика НЕ смешивает различные статусы в одну «зелёную» финансовую оценку.
6. Далее через существующие `DecisionPlaybookRegistry` и `DecisionScenarioEngine` рассчитываем **только явно заданные** альтернативы после подтверждения фактов. Реальный интегрированный React/Keycloak E2E остаётся будущей задачей.

## 5. Критерии приёмки

- `CrossFormDiagnosticEngineTest`: независимые числовые goldens F01 + F02 + F03 + cash, все шесть правил, расхождение cash=5, неполные данные, дубли, период/валюта/ACTUAL rejection, гипотеза без причинности.
- `TrustedCrossFormDiagnosticIntegrationTest`: Testcontainers PostgreSQL: версионированный исходник -> проверенное поле -> immutable origin -> sealed population -> published FactSet -> cross-form findings -> immutable snapshot -> re-open/idempotency/tenant denial.
- `CrossFormEvidencePlannerTest`: только F02 -> рекомендации F03 и F01; никакого «заполните все формы», уже существующую F02 с пропусками просить исправить, отсутствие якорного факта не запускает полную загрузку каталога.
- CI: эти три тестовых класса должны входить в fail-closed evidence gate на одном SHA (Node/Java/PostgreSQL/Chromium Linux+macOS).

## 6. Следующая расширяемость — R4.6

1. Реестр `IndicatorRelationshipRegistry` за пределами пилота: валидируемые описания рёбер (metric keys/versions, role, definition, scope/period/calendar, valid reporting basis, sector/applicability, type, qualification, responsible expert, numeric goldens, source requirements). Никогда не создавать автоматическую связь по совпадению русского/казахского/английского названия.
2. `DynamicEvidenceGraph` по всем применимым отчётным формам: для каждой методики строить транзитивно нужные входы, но запросы пользователю ранжировать по ближайшему доступному результату, с отсутствующими периодами/полями и ожидаемой диагностической пользой. Отсечь циклы зависимостей и повторное использование одинаковых финансовых событий.
3. F01/F02/F03: 3–5 лет, сопоставимость учётной базы, cash-flow adjustments, working capital bridge, DSCR/CCC по утверждённой политике; затем торговля, услуги, производство и остальные сектора.
4. Отдельные механизмы финансовой **сверки**, причинно-согласованной факторной декомпозиции и статистической корреляции. Для Pearson/Spearman не использовать поперечное сравнение одного месяца как доказательство статистической корреляции.
5. Production OIDC/ABAC, версионированный XLSX и React, независимая экспертная S2-квалификация и реальные пользователи. Ни один чекбокс «код реализован» не заменяет приёмку.

**Решение:** R4.5 backend SYNTHETIC-пилот может быть принят только после полного однокоммитного GREEN. Production/HOLD до методик, безопасности и пользовательского E2E.
