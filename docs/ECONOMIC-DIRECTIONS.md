# FIN Project Marketplace — дополнительные экономические направления и FIN Project Marketplace

**Версия:** ECONOMIC-DIRECTIONS v1.1 · **Дата:** 2026-11-15  
**Статус:** PROJECT REQUIREMENTS / NOT IMPLEMENTED  
**Основное ТЗ:** [FIN-ANALYZER-PROJECT-TZ.md](FIN-ANALYZER-PROJECT-TZ.md)

## 1. Назначение

FIN Analyzer — адаптивная экономическая платформа, которая помогает пользователю понять экономический вопрос, собрать данные, провести прозрачные расчёты, сформировать бизнес-план, подготовить безопасную версию для передачи адресатам и впоследствии отслеживать исполнение.

Все направления должны работать на **одной модели экономических фактов, допущений, периодов, валют, единиц, источников и версий**. Не допускается создание разных независимых калькуляторов, дающих противоречивые показатели одного проекта.

**Базовые направления:** Financial Advisor (FIN), Investment Advisor (INV), Marketing Advisor (MKT), Operations & Production Advisor (OPS), Business Plan Builder (BP). Они сохраняются. Следующие 12 направлений — расширение общего продукта.

## 3. Общий маршрут адаптивного мастера

1. **Вопрос пользователя:** «Нужен инвестор», «Оценить бизнес», «Оптимизировать закупки», «Открыть филиал», «Подготовить бизнес-план» и др.
2. **Профиль:** стадия бизнеса S0–S4, основной/дополнительные коды ОКЭД, география, юридическое лицо или проект, цель.
3. **Доступные данные:** простые ответы, React-таблица, поформный XLSX, CSV/учётная выгрузка, журнал операций, позже голос/фото как непроверенный черновик.
4. **Правила форм:** `DomainRequirementRegistry` предлагает только применимые модули F/C/P/T/D/B, новые поля/измерения — если они необходимы для целевого расчёта.
5. **Проверка:** отдельные состояния `MISSING/EXPLICIT_ZERO/ESTIMATED/NOT_APPLICABLE/PRESENT`; проверка валюты, периода, двойного счёта и допустимости расчётов.
6. **Диагностика:** точные формулы, список допущений и недостающих данных, сравнение альтернатив, следующий наиболее полезный вопрос.
7. **Отчёт:** Business Plan / Valuation / Funding / Operations / Investor Teaser / Risk Report — из общего версионированного `AnalysisSnapshot`.
8. **Продолжение:** вернуться к проекту, уточнить финансовую модель, сравнить старые и новые сценарии; для hosted-функций — отдельный доступ и добровольная публикация.

Мастер должен поддерживать несколько направлений в одном кейсе. Например, открытие магазина требует STRAT + INV + MKT + SUP + HR + TAX + RISK + BP, но вопросы показываются поэтапно и без обязательного заполнения всех модулей.

## 4. Полный Business Plan Builder

Бизнес-план — **вычисляемая модель с доказательствами, а не только генератор текста**.

**PLAN-01. Варианты:** собственный план / инвестор / банк / грант / партнёрство / франшиза / развитие существующего бизнеса.

**PLAN-02. Разделы:** резюме проекта, компания и продукт, ОКЭД/регион, рынок и клиент, конкуренты (источники, дата), продажи и маркетинг, производство/операции и снабжение, команда, юридические/налоговые предпосылки, CAPEX, оборотный капитал, источники финансирования, прогноз P&L, Cash Flow, Balance (если модель достаточна), инвестиционные показатели, анализ риска, сроки, планы действий, приложения.

**PLAN-03. Факты и предположения:** каждый тезис `FACT / CALCULATED / ASSUMPTION / USER_STATEMENT / EXTERNAL_REFERENCE / UNVERIFIED`; никакие значения рынка, конкурентов, налогов или объёмов не придумываются автоматически.

**PLAN-04. Связность:** изменение цены/спроса/себестоимости должно воспроизводимо менять выручку, cash flow, NPV, срок окупаемости, риски, графики и инвестиционный teaser. При изменении сценария ранее сформированный бизнес-план становится `STALE`, пока не пересчитан.

**PLAN-05. Аудитория:** на основании одного проекта формировать разные разрешённые представления: полный управленческий план, пакет для банка, краткая презентация инвестору, grant dossier, franchise case.

**PLAN-06. Прогнозы:** сценарии baseline/upside/downside, `forecastAsOf`, версия допущений, начало проекта, горизонт, частота, ставка дисконтирования. Исторические факты не заменяются прогнозными значениями.

**PLAN-07. Экспорты:** локальный `.fin.json`, versioned PDF/HTML, структурные XLSX-таблицы, `PublicTeaserSnapshot`; формат считается готовым только после cross-format parity тестов.

## 5. Публикация бизнес-планов: SHARE, MARKET, FUND

### 5.1. Контуры безопасности

**FIN Core — локальный:** по умолчанию все данные только на устройстве. В MVP возможен пользовательский экспорт `PublicTeaserSnapshot`, HTML/PDF/JSON и самостоятельная пересылка. Не обещать живой поиск инвесторов или отзыв доступа без сервера.

**Backend stack for hosted FIN Connect:** React + Spring Boot BFF; Keycloak (OIDC), Redis (sessions/cache), RustFS (private file storage), KumoMTA (email) and PostgreSQL (system of record) integrate only on the server side. No direct React → Redis/RustFS/KumoMTA/Keycloak Admin traffic. Auth UI is presented only via protected reverse proxy. See [ADR-008](ADR-008-FIN-CONNECT-BACKEND-STACK.md).

**FIN Connect — отдельный hosted-сервис (future):** аккаунты, право представлять компанию, каталог проектов, приглашения, доступ по документам, сообщения, запросы инвесторов, Data Room, журнал обращений, модерация и удаление согласно правовым требованиям. Должен быть полностью добровольным дополнением к FIN Core, без принудительной загрузки частных данных.

**Постоянная граница FIN Project Marketplace (OUT OF SCOPE):** FIN не принимает, не хранит и не переводит деньги, не организует биржевые торги, краудфандинговые инвестиционные операции, подписку на финансовые инструменты или исполнение сделок и договоров. Стороны осуществляют финансирование и юридические действия вне FIN; FIN допускает только информационные контакты, обмен разрешёнными материалами и ссылку на внешний факт при подтверждении. См. [ADR-007](ADR-007-FIN-PROJECT-MARKETPLACE.md).

### 5.2. Режимы публикации

| Статус | Аудитория | Разрешение |
|---|---|---|
| PRIVATE | только локальный владелец | полная финансовая модель и документы не публикуются |
| PREVIEW | пользователь проверяет будущий публичный вид | интерактивная подсветка исключённых приватных полей |
| PUBLIC_TEASER | пользователи/поисковые системы, если явно разрешено | исключительно allowlisted краткие сведения, округлённые/публично согласованные цифры |
| INVITE_ONLY | выбранные адресаты | выбранные разделы/документы, время доступа, версия |
| DATA_ROOM | проверенные приглашённые, при необходимости после NDA | поимённые разрешения, журнал доступа, ограниченный набор файлов |

**Особое требование:** не передавать исходный `.fin.json` или полный BusinessPlanCase вместо публичного teaser. Отдельный `DisclosurePolicy` задаёт разрешённые значения, документы, графики и метаданные. Все данные закрыты по умолчанию. При скачивании инвестором документ нельзя гарантированно «отозвать» — отзыв блокирует только будущий hosted-доступ.

### 5.3. Жизненный цикл инвестиционного проекта

`DRAFT → INTERNAL_REVIEW → APPROVED_FOR_SHARING → PUBLISHED → PAUSED/ARCHIVED`. Для нового финансового сценария создаётся новая версия `PublicTeaserSnapshot`, старый опубликованный документ не переписывается.

Инвесторская коммуникация: `INTEREST_REQUEST → QUESTIONS → MEETING → DUE_DILIGENCE_REQUEST → DOCUMENT_EXCHANGE → EXTERNAL_TERM_SHEET/AGREEMENT → CLOSED/WITHDRAWN`. Запрос интереса не равен обещанию инвестирования, статус «сделка» не равен фактическому поступлению денег. Договор и расчёты — отдельный проверяемый правовой процесс.

### 5.4. Funding Navigator

При выборе механизма (собственные средства, кредит, долевое участие, лизинг, грант, субсидия, гарантийная поддержка и пр.) FIN собирает `FundingRequirement`: сумма, валюта, инструмент, срок, назначение, собственный вклад, обеспечение, документальные требования, риски.

Программы финансирования хранятся как `FundingProgramDefinition` с полями: источник/ссылка, юрисдикция, effectiveDate, reviewDate, условия применимости, eligibility rules, валюта, limitations. Результат может быть лишь `POSSIBLY_APPLICABLE/INAPPLICABLE/INSUFFICIENT_DATA/NEEDS_CURRENT_VERIFICATION` без утверждений о реальной доступности, гарантированной ставке, одобрении или юридическом праве на получение.

## 6. Оценка бизнеса и сравнение финансирования

- DCF на раздельных проектных и собственных денежных потоках; учёт долга и денег при переходе Enterprise Value → Equity Value.
- Ставка дисконтирования, терминальная стоимость, горизонты, условные сценарии, sensitivity обязательны для любых NPV/valuation выводов.
- Multiples — только при сопоставимых компаниях/сделках, определённой метрике, дате и источнике; без недоказанных коэффициентов «по отрасли».
- Привлечение капитала: сумма инвестиции, pre/post-money (если выбрана соответствующая модель), размытие доли, стоимость обслуживания долга, влияние ковенант и cash flows.
- Ни один расчёт не является сертифицированной оценкой бизнеса, предложением продать долю или гарантированной доходностью.

## 7. Общая техническая модель

Предложенные сущности (не реализованы в текущем FIN-R1A):
- `EconomicCase, BusinessProfile, ActivityCodeVersion, EconomicScope, FinancialFact, AssumptionSet`;
- `BusinessPlanCase, BusinessPlanSection, EvidenceRegister, AnalysisSnapshot, ReportSnapshot`;
- `FundingRequirement, FundingProgramDefinition, InvestmentAlternative, ValuationCase`;
- `DisclosurePolicy, PublicTeaserSnapshot, PublishedVersion, ShareGrant`;
- будущий hosted-контур: `CompanyAccount, RepresentativePermission, InvestorProfile, ProjectListing, InterestRequest, DataRoomResource, AccessAudit, ModerationCase`;
- `ExecutionBaseline, Milestone, BudgetActual, InvestorUpdateSnapshot`.

**Неподменяемые связи:** одна ревизия финансовых фактов → выбранный scenario/assumption set → deterministic formulas → AnalysisSnapshot → BusinessPlanCase/InvestorTeaser/InvestorUpdate. Два отчёта из одной версии сценария не могут содержать разные NPV/выручку/валюту без явно указанной трансформации.

## 8. Роли и границы доверия hosted-контуров

Будущие роли `BUSINESS_OWNER, BUSINESS_EDITOR, FINANCIAL_ANALYST, INVESTOR, VERIFIED_LENDER, PLATFORM_MODERATOR`, per-project и per-document ACL с deny-by-default. «Владелец учётной записи» не равен автоматически юридически уполномоченному директору. Для публичной публикации могут понадобиться подтверждение представительства, защита от мошенничества, управление согласиями и модерация.

Ни одна рекламная/платёжная/маркетинговая интеграция не должна получать данные из полного бизнес-плана по умолчанию.

## 9. Модели исполнения и мониторинга

После привлечения финансирования (подтверждённого во внешнем процессе) FIN:
- замораживает `ExecutionBaseline` с исходными прогнозами, графиком освоения CAPEX и KPI;
- принимает факт по периодам через все разрешённые адаптеры;
- считает план-факт, срок, освоение бюджета, отклонения и пересмотр cash runway;
- формирует отчёт инвестору из согласованного snapshot и отмечает непроверенные данные;
- не утверждает выполнение юридических обязательств только по состоянию задач.

## 11. Приёмочные сценарии и негативные тесты

- `ECON-01`: пользователю ИП доступны простые вопросы, нет требования заполнить F01–F04.
- `ECON-02`: для указанного ОКЭД без проверенного отраслевого пакета отображаются только универсальные применимые расчёты, без выдуманных sector KPIs.
- `ECON-03`: на одном сценарии числа в маркетинге, инвестициях, бизнес-плане, Dashboard и экспорте совпадают.
- `ECON-04`: изменение спроса обновляет выручку, unit economics, P&L, cashflow и NPV; старый report snapshot остаётся неизменным.
- `ECON-05`: рост расходов или CAPEX меняет срок окупаемости/финансирование только через проверяемые формулы; неверный IRR = NOT_COMPUTABLE.
- `ECON-06`: cash receipt ≠ revenue; inventory purchase ≠ COGS; loan proceeds/owner funding ≠ income.
- `ECON-07`: небезопасная строка не становится Excel-формулой при экспорте; XLSX/CSV/JSON импорт не изменяет утверждённую версию без review.
- `SHARE-01`: публичный teaser никогда не содержит private salary/payroll, bank account, raw .fin.json, персональные данные и скрытые поля/графики.
- `SHARE-02`: до публикации пользователь видит и утверждает точный preview; без действий пользователя нет публикации и передачи данных.
- `SHARE-03`: изменение сценария создаёт новый опубликованный snapshot, не переписывая предыдущий.
- `SHARE-04`: `INVITE_ONLY` запрещает доступ по чужому/истёкшему токену; отзыв блокирует будущие запросы, но не уже скачанный файл.
- `SHARE-05`: инвестор не может запросить документ за пределами прав проекта; каждый запрос аудируется.
- `FUND-01`: условия программы с устаревшей датой не объявляются действующими; пользователь направляется к официальному источнику.
- `VAL-01`: проверены sign convention, enterprise/equity bridge, терминальная стоимость, ставка и сценарная чувствительность.
- `EXEC-01`: зафиксированный baseline не меняется при повторном планировании; план-факт и Investor Update воспроизводимы.
- `LEGAL-01`: в FIN отсутствуют любые механизмы приёма/перевода/хранения денег, биржевых торгов, исполнения сделок и внутреннего юридически обязательного инвестирования; это постоянная продуктовая граница, не будущий релиз.
- `PRIV-01`: локальный Core не требует авторизации/облака/БД; периметр данных и добровольность загрузки тестируются браузерным E2E.
- `UAT-01`: фактические владельцы бизнеса, инвесторы и финансовые специалисты подтверждают понятность отчётов и недостаточных данных.

Для каждого направления требуются отдельные golden fixtures (корректные/некорректные), unit/contract tests, E2E пользовательского сценария, проверка форм и независимый S2 review финансовых, security и юридически чувствительных решений.
