## 1. Что сейчас разрабатываем, а что отложено

**Текущая цель:** пользователь выбирает финансовый проект → финансовую форму → язык → **учётный период** → видит понятную React-форму либо скачивает **равнозначный, удобный Excel-шаблон**, заполняет его и загружает → оба пути дают **одинаковый нормализованный набор данных и ValidationReport**, привязанный к проекту. Далее существующий процесс review/publication остаётся в архитектуре, но первичная приёмка этой итерации — **согласованная загрузка**.

### В ближайшую реализацию (IN SCOPE)

- Единый версионированный словарь `FormDefinition → FieldDefinition → LabelTranslations (ru/kk/en) → ValidationRules`.
- Единый стандарт `ReportingPeriod` для WEEK / MONTH / QUARTER / HALF_YEAR / YEAR и для остатков AS_OF (при необходимости CUSTOM как расширение, не обязательный пилот).
- Учётная валюта `project.accountingCurrency`; валюта отчёта, при необходимости валюта строки и отдельный масштаб денежных сумм.
- Единая генерация React и Excel из одной схемы, читаемый UX, единые серверные проверки.
- Привязка формы и результата загрузки к `projectId`; проверка согласованности project + template + form + period + currency в backend. Не считать локальный `.fin.json` полноценным серверным проектом.
- Пилот на F02 (месяц), F01 (остаток на дату), F03 (месяц), затем тесты на все виды периодов; далее расширение словаря.

### Вынести из текущего P0 (OUT OF SCOPE)

- **Новые работы по Keycloak, OIDC/JWT, bearer-token, ABAC, ролям, отзыву токенов, тестам двух пользователей и развёртыванию IAM.** Bearer-token планируется, но не входит в этот этап.
- Разработка «стратегического компаса», удобного интерфейса выбора методов анализа, новых KPI, финансовых рекомендаций, новых межформенных методик и расширение расчётного каталога.
- Продвинутая финансовая квалификация S2 для новых методик и развёртывание production.

**Важная граница:** имеющийся backend с закрытыми финансовыми endpoints НЕ делать публичным. `FIN_SECURITY_ENABLED=false` в существующей реализации означает deny-all, а не anonymous access. Для разработки загрузки использовать unit/contract/интеграционные тесты через сервисы и БД и/или строго изолированный UAT fixture; не добавлять небезопасный production bypass. Настоящий browser↔backend E2E, зависящий от bearer token, получает статус BLOCKED/DEFERRED, пока нет штатного проверенного способа входа.

## 3. Процесс A — словарь форм и генерация шаблонов

### 3.1. Единая версия схемы

- `FormDefinition(formCode,formVersion,formKind,periodPolicy,allowedPeriodTypes,sourceRowPolicy,fields,translations,rules,schemaHash,status)`.
- `FieldDefinition(fieldCode,metricCode?,displayOrder,required,kind,unit,decimalPrecision,allowedValueRange,rowCardinality,timeRole,translations)`.
- `translations = {ru,kk,en}`: название формы, заголовки, имена полей, help text и сообщения ошибок. `kk` — код казахского языка; `kz` не писать в persisted language-code.
- `projectBinding = (projectId,projectVersion,accountingCurrency,fiscalCalendarId)`; выбирается для генерации шаблона, но **не является частью глобальной схемы формы**.
- `schemaHash` покрывает функциональную структуру/правила/типы; `displayTranslationVersion` отдельно фиксирует версию видимых переводов, чтобы правка орфографии не меняла арифметическую семантику.
- Редактирование `ACTIVE`-версии запрещено; новая версия выпускается отдельно. 166 форм в каталоге ≠ 166 готовых к вводу схем; для остальных показывать `SCHEMA_NOT_READY`, а не генерировать произвольную структуру.

### 3.2. Читаемый Excel: три зоны

**Лист `FIN_Data`**, объединять ячейки метаданных и таблицы только так, чтобы не мешать механическому чтению. Показанный пример — *условные данные*, не финансовая отчётность клиента.

| Строка | A | B | C | D | E | F | G |
|---|---|---|---|---|---|---|---|
| **1 — паспорт** | `F02` — код формы | `ru` — язык | `2026.10` — период | `Отчёт о прибылях и убытках` — название | `KZT` — валюта отчёта | `1` — масштаб: единицы | `FIN-DEMO` — проект |
| **2 — шапка RU / KK / EN** | Код строки / Жол коды / Row ID | Код поля / Өріс коды / Field code | Наименование / Атауы / Item | Значение / Мәні / Value | Валюта / Валюта / Currency | Примечание / Ескертпе / Note | Период строки / Жол кезеңі / Row period |
| **3+ — данные** | `pnl` | `netRevenue` | Чистая выручка | `400` | `KZT` | необязательно | `2026.10` |
| **4** | `pnl` | `cogs` | Себестоимость | `260` | `KZT` | необязательно | `2026.10` |

**Ограничения:**

- Формат первой строки должен быть одинаковым для всех пяти периодических типов; `C1` — видимый **код выбранного периода**, `D1` — название отчёта на выбранном языке; `E1` — валюта отчёта ISO 4217; `F1` — масштаб `1|1000|1000000`; `G1` — человекочитаемый код проекта. Лейблы паспорта дать в подсказках/стиле/непосредственно над ячейкой без сдвига номера строки. Машинные позиции A1:G1 фиксированы.
- Вторая строка — заголовки **сразу на трёх языках**. Можно размещать RU/KK/EN в одной ячейке с переносами строк для лучшей читабельности; при чтении парсер сравнивает опубликованный layout version, а не использует подпись как идентификатор.
- `sourceRowId` и `fieldCode` видимы, защищены от случайного редактирования без требования пароля; названия строк C3+ показываются на выбранном языке. Для детальных ведомостей допускаются повторяющиеся field codes при уникальных row ID.
- Для формы с фиксированным периодом `G3:Gn` автоматически заполняется и по возможности защищается; для допустимого mixed-period detail его заполняет пользователь из определённого набора.
- Лист `_FIN_Metadata` (veryHidden) закрепляет `formatVersion`, `formVersion`, `schemaHash`, `displayTranslationVersion`, `projectId`, `projectVersion`, `periodType`, `periodCode`, `startInclusive`, `endExclusive`, `asOfDate`, `calendarId`, `accountingCurrency`, `reportCurrency`, `amountScale`, `templateInstanceId`. Метаданные служат проверке согласованности, **не авторизации**.
- Цвет/UX: лёгкий контрастный заголовок, читаемые ширины, переносы трёхъязычных заголовков, заморозка 2 строк, подсветка *только* доступных для ввода ячеек, число/валюта с понятным форматом, выпадающие списки там, где разрешено, подсказки и короткий лист `Instructions` при необходимости. Если добавлен `Instructions`, контракт перечисляет листы явно.
- Переводы помогают понять поля, а не определяют смысл; менять подпись без изменения `fieldCode` безопасно, но revision перевода фиксируется.
- Ни один пустой ввод не превращать в `0`; для нулей требуется явный `0`.
- Запрещены формулы, внешние ссылки, неожиданные листы, поля или скрытые денежные значения. Для денег использовать строковое/decimal-safe представление с проверкой precision, не округлять `BigDecimal` через двоичное число Excel.

### 3.3. React из той же схемы

Сначала проект, затем `formCode`, язык, **тип периода** из `allowedPeriodTypes`, конкретный период, валюта и масштаб по политике формы. Форму отрисовывать динамически:

- Имя поля + локализованная подсказка + стабильный `fieldCode` (в tooltip или компактной подписи), единица/масштаб/валюта; поле ввода с понятным местом для значения.
- Финансовые показатели группировать (доходы, затраты, баланс и т. д.). Использовать единые названия и порядок в React и Excel.
- Не путать `NULL/отсутствует` и `0`; точные числовые строки и серверная проверка.
- Обязательные поля отмечать; ошибки показывать рядом с полем и в сводке, с одинаковыми `ruleCode` в React и Excel.
- Для повторяющихся строк — кнопки добавить/удалить, устойчивый row ID, запрет дубликатов.
- Явные действия: `Скачать Excel`, `Проверить`, `Сохранить черновик`, `Отправить на загрузку`. Пока нет серверного project contract, нельзя имитировать успешную публикацию.

## 4. Единый стандарт времени FIN — ReportingPeriod V1

**Принцип:** нельзя считать весь мир месячным. Для любого периода хранить *тип*, *канонический код*, *календарь*, *начало включительно*, *конец не включительно*, а для остатков — *дату среза*. В интерфейсе пользователь видит понятную метку; backend работает с проверенным canonical period.

| Тип `periodType` | Код в Excel `C1` / API | Отображение RU (пример) | Интервал учёта |
|---|---|---|---|
| `WEEK` | `2026-W03` | Неделя 03 · 12–18 янв. 2026 | Пн 2026-01-12 … Пн 2026-01-19 (не включ.) |
| `MONTH` | `2026.10` | Октябрь 2026 | 2026-10-01 … 2026-11-01 |
| `QUARTER` | `2026-Q3` | III квартал 2026 | 2026-07-01 … 2026-10-01 |
| `HALF_YEAR` | `2026-H2` | II полугодие 2026 | 2026-07-01 … 2027-01-01 |
| `YEAR` | `2026` | 2026 год | 2026-01-01 … 2027-01-01 |
| `AS_OF` | `2026-10-31` | На 31 октября 2026 | Срез на конкретную дату, НЕ сумма потоков |

**Правила:**

1. Неделя — ISO 8601: понедельник–воскресенье, ISO *week-based-year*, 52/53 недели, неделя может переходить через границу календарного года. Например `2026-W01` начинается **2025-12-29**. `2026-W54` запрещён; `2026-W53` принимать, только если ISO-календарь допускает.
2. Месяц `YYYY.MM` в **видимом Excel** сохраняется по ранее согласованному UX. Сервер нормализует к `YearMonth`, в запросах допустим только один утверждённый формат; `2026.13` и `2026.1` невалидны.
3. Квартал и полугодие по умолчанию календарные, но если у проекта нестандартный финансовый год, *обязателен* `fiscalCalendarId` и версия календаря. Код `FY2026-Q1` нельзя интерпретировать как `2026-Q1` без финансового календаря. В V1 финкалендарь фиксируется как `ISO_CALENDAR` и non-calendar fiscal forms получают `UNSUPPORTED_FISCAL_CALENDAR`.
4. `AS_OF` отличается от интервала: остаток на 31.10 не суммируется за октябрь. Для F01 можно выбирать месяц и автоматически вычислять дату окончания или явно выбирать `AS_OF` **только если разрешено версией формы**; иначе reject.
5. **Единая функциональная модель**:
   ```text
   ReportingPeriod {
     type: WEEK | MONTH | QUARTER | HALF_YEAR | YEAR | AS_OF,
     code: string,
     calendarId: string, calendarVersion: string,
     startInclusive?: LocalDate,
     endExclusive?: LocalDate,
     asOfDate?: LocalDate,
     displayLabel: {ru:string, kk:string, en:string}
   }
   ```
   Даты вычисляет сервер, браузер не может их свободно назначить. Для `AS_OF` разрешена одна дата среза; `start/end` для оборотов неприменимы.
6. Нельзя складывать остатки `AS_OF` из нескольких месяцев; обороты можно агрегировать по разрешённым правилам **только при полном и непересекающемся покрытии**. Текущий месяц, квартал и год нельзя объединять как независимые строки, если они перекрываются: иначе двойной счёт.
7. Версии, сравнения и корректировки: `(projectId,formCode,formVersion,periodType,periodCode,calendarVersion,reportingBasis,reportCurrency,sourceRevision)` — основа идентичности отчёта. Дублирующие загрузки получают deterministic conflict/revision policy.
8. Незаполненный отчётный период — ошибка; если форма допускает многопериодные строки, каждая имеет утверждённый тип периода и код, совместимый с layout.

## 5. Учётная валюта, валюта формы и денежные единицы

**Учётная валюта проекта** — обязательный `project.accountingCurrency` в ISO 4217 (`KZT`, `USD`, `EUR` и т. д.). Это основная валюта ведения учёта/сопоставления, заданная проектом. При первом создании проекта может предлагаться `KZT`, **но пользователь должен видеть и подтвердить её**. После публикации фактов смена учётной валюты без новой версии project context и явной конверсионной политики запрещена.

| Поле | Назначение | Где задаётся |
|---|---|---|
| `accountingCurrency` | Учётная валюта проекта | Project context, read-only при вводе |
| `reportCurrency` | Валюта итоговых сумм формы | В шапке React и `E1` Excel; по умолчанию из проекта |
| `rowCurrency` | Валюта конкретной операции | Колонка `E3+` при multi-currency формах |
| `amountScale` | Единицы `1`, тысячи `1000`, миллионы `1000000` | Отдельная шапка React и `F1` Excel |
| `fxPolicyVersion` / `exchangeRateSource` | Политика и источник пересчёта, если он разрешён | Отдельная методика/справочник, в ближайший P0 не реализуем |

**Правила:**

- Для моновалютной формы `reportCurrency = project.accountingCurrency` по умолчанию; если отличается — `CURRENCY_POLICY_MISMATCH` или отдельный маршрут `FX_CONVERSION_REQUIRED`, **не** молчаливое изменение валюты.
- В мультивалютной ведомости операция `rowCurrency` может быть USD или EUR при учётной KZT. Сохраняем **исходную валюту и оригинальную денежную сумму**; без согласованного курса и даты пересчёта не создаём «эквивалент KZT» и не суммируем разновалютные значения.
- **Денежная валюта ≠ единица измерения ≠ масштаб.** Например, `KZT` + `1000` означает тысячи тенге; `USD` + `1` означает доллары. Эти координаты обязаны входить в versioned submission и validation.
- Столбец `Валюта` в таблице обязателен для многовалютных строк и автоматически заполняется/защищён для моновалютных; код валюты буквенный ISO 4217, без знаков `₸,$,€` в data key.
- Нет пересчёта по текущему курсу сети «на лету». Разработка курсов и FX-политик — будущий этап; до неё несовместимые валюты возвращают `FX_POLICY_NOT_CONFIGURED` / `NOT_COMPARABLE`.
- Decimal хранить и передавать строкой; server `BigDecimal` выполняет умножение на `amountScale` ровно один раз. Никакого двойного применения масштаба при повторном импорте; независимые tests `1`, `1000`, `1000000`.
- Для неденежных показателей (штуки, тонны, %, дни) валюта **не прикрепляется к значению автоматически**; `FieldDefinition.unit` определяет тип. У проекта учётная валюта всё равно остаётся.

## 6. Процесс B — ввод по проекту, общий normalizer

**Единый путь:**
```
Project selected
  → (form code + published form version + locale + ReportingPeriod + currency/scale)
  → FormSchema
  ├─ React Form Renderer → structured raw rows ─┐
  └─ Excel Template V2 → XLSX parser → raw rows ─┤
                                                  ↓
                                    CanonicalFormSubmission
                                                  ↓
                           FormValidator (same rules and codes)
                            ├─ errors → field/Excel coordinate
                            └─ valid → immutable project-bound intake
```

Пользователь сначала выбирает проект. На данном этапе можно проверять, что `projectId` существует, проект активен, а template и выбранный проект совпадают. Это **не заменяет будущую проверку полномочий по bearer-токену**. Проект должен иметь стабильный UUID и `projectVersion`. В Excel `G1` — читаемый `projectCode`, `projectId` — в `_FIN_Metadata`. При загрузке сравнить `selectedProjectId` из запроса и `template.projectId` и resolved server project context. Несовпадение → `PROJECT_CONTEXT_MISMATCH`; никаких автоматических перепривязок к имени компании.

**Canonical DTO:**
```json
{
  "projectId": "server-project-uuid",
  "projectVersion": 1,
  "formCode": "F02",
  "formVersion": "FIN-FORM-V2",
  "schemaHash": "sha256-of-published-schema",
  "locale": "ru",
  "reportingPeriod": {
    "type": "MONTH",
    "code": "2026.10",
    "calendarId": "ISO_CALENDAR"
  },
  "accountingCurrency": "KZT",
  "reportCurrency": "KZT",
  "amountScale": 1,
  "inputMode": "MANUAL",
  "rows": [
    {"sourceRowId":"pnl","fieldCode":"netRevenue","rawValue":"400","rowCurrency":"KZT"}
  ]
}
```
Объект иллюстративный: `projectId` и поле валюты должны дополнительно сверяться с server project context; `accountingCurrency` не принимается как право пользователя её изменить; `inputMode` отдельно равен `MANUAL` или `XLSX`.

**ValidationReport** одинаков для обоих каналов:
```json
{
  "status": "VALID|INVALID",
  "formCode": "F02",
  "formVersion": "FIN-FORM-V2",
  "projectId": "server-project-uuid",
  "periodCode": "2026.10",
  "accountingCurrency": "KZT",
  "reportCurrency": "KZT",
  "findings": [{
    "ruleCode": "REQUIRED_FIELD_MISSING",
    "fieldCode": "cogs",
    "sourceRowId": "pnl",
    "excelCell": "FIN_Data!D4",
    "messageKey": "validation.required"
  }]
}
```

Порядок проверки: project/form/version/calendar/period/currency/scale → разрешённые колонки и строки → типы/precision → required/zero/duplicate → финансовые методики только где квалифицированы → нормализованное сохранение. Ошибки Excel показывать с координатой ячейки и тем же `ruleCode`, что в React.

**Инвариант parity:** одинаковые исходные значения, `project`, `formVersion`, `period`, `currency`, `scale` → одинаковые canonical rows и те же ошибки (независимо от input channel), кроме явных `sourceFormat` и `rawSourceSha`. Загрузка не равна автоматическому review/публикации и не запускает «стратегию анализа».

## 7. Минимальные API и реализационные пакеты

API (проектное предложение; ещё НЕ реализовано):

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/v2/form-catalog/{formCode}/schema?version=&lang=` | Типизированная схема, три языка и допустимые периоды |
| GET | `/api/v2/projects` | Доступные проекты (без текущей работы над IAM; реальный доступ позже) |
| GET | `/api/v2/projects/{projectId}/forms/{formCode}/template?periodType=&periodCode=&lang=` | Серверный readable XLSX V2 |
| POST | `/api/v2/projects/{projectId}/form-intake/validate` | Общий ValidationReport |
| POST | `/api/v2/projects/{projectId}/form-intake/manual` | Project-bound validated submission |
| POST | `/api/v2/projects/{projectId}/form-intake/xlsx` | Ровно тот же результат + raw XLSX digest |

**Важно:** это спецификация маршрутов; не открывать их без действующего backend access control. В данном этапе доказываем сервисы через интеграционные тесты / контрактные fixtures. Не реализовывать новые token handlers.

**Приоритетная последовательность**:

- **I0 Contract/RED:** FormSchema + ReportingPeriod + MoneyContext + ProjectRef и примеры XLSX/React для 5 форм, onafh. Golden/negative tests.
- **I1 Registry and calendar:** versioned PostgreSQL definitions и единый period resolver; независимые goldens week/quarter/half-year/year/as-of, включая ISO week-year boundary.
- **I2 Shared form renderer:** React и Excel из одной схемы, удобочитаемое оформление, RU/KK/EN, видимые период и валюта.
- **I3 Unified parser/validator:** нормализация, BigDecimal/scale, empty vs zero, project/currency match, negative xlsx.
- **I4 Project-bound intake:** safe mapping к существующей publication schema, запрет чужого проекта и silent overwrite; **не добавлять IAM**.
- **I5 Focused smoke:** не массовые нагрузочные тесты. Проверить прямой пользовательский путь + отрицательные случаи на тестовом контуре.

**Стратегический выбор методов анализа / smart compass UX / Bearer Token IAM** — отложены до доказанной устойчивой загрузки.
