# FIN Analyzer — roadmap, тестовая стратегия и приёмка

**Версия:** 1.0 · **Статус:** PLAN / NOT IMPLEMENTED  
Источники требований: [FIN-SPEC](FIN-SPEC.md), [ARCHITECTURE](ARCHITECTURE.md), [FORM-CATALOG](FORM-CATALOG.md).

## 1. Принципы выполнения

- Сначала работающий пользовательский путь, затем расширение сценариев.
- «IMPLEMENTED» не равно «ACCEPTED». Функция закрыта только при зелёных доменных, компонентных и E2E-тестах, а также ручной визуальной проверке важных экранов.
- На каждом шаге новый код не должен повреждать утверждённые локальные FIN-проекты.
- Не создавать параллельные функциональные ветки без необходимости. Документация стартует в main; для разработки допускается одна согласованная рабочая ветка с PR, без merge до приёмки.
- Отсутствие внешнего Backend/БД — проверяемое архитектурное ограничение MVP.

**MVP:** FIN-R0…R7 с 3 стратегиями: FINANCIAL_HEALTH, COUNTERPARTY_RISK и MANAGEMENT_ANALYSIS. ## 4. XLSX negative/security matrix

| ID | Файл / атака | Ожидаемый результат |
|---|---|---|
| XLS-01 | Корректный шаблон каждого из 4 типов | Импорт без потери исходных значений |
| XLS-02 | Неверный templateVersion | Безопасный отказ |
| XLS-03 | XLSM вместо XLSX | Отказ |
| XLS-04 | Пропущен технический лист | Отказ |
| XLS-05 | Дублирован metric code | Отказ |
| XLS-06 | Переставленные заголовки/локаль | Значения привязаны к стабильным кодам; несовместимость выявлена |
| XLS-07 | Формула вместо числового ввода | Отказ с адресом ячейки |
| XLS-08 | Строка с внешней ссылкой | Никаких сетевых обращений; недопустимое содержимое отклонено |
| XLS-09 | Несоответствие валюты и контекста | BLOCKER |
| XLS-10 | Разрушенный XLSX/zip bomb | Ограничение ресурсов, сообщение об ошибке |
| XLS-11 | Импорт при существующей APPROVED ревизии | Исходная утверждённая ревизия не изменена |
| XLS-12 | Изменение одного значения на 1 единицу | Новый diff; валидация и пересчёт |
| XLS-13 | Метка таблицы начинается с =/@/+ | Безопасный текст при повторном экспорте |

## 5. Indicator & Strategy tests

- Для каждой финансовой формулы: положительный, нулевой, отрицательный, отсутствующий операнд, масштаб, граничная точность.
- Для графа формул: сложная зависимость, неизвестная метрика, цикл, повторное использование результатов, смена версии формулы.
- Для каждого правила стратегии: true / false / not-evaluated, минимальные/максимальные пороги, отраслевое исключение.
- Сравнение 2023/2024/2025 должно соблюдать период и basis. Нельзя смешивать годовую и квартальную выручку без корректного приведения.
- При изменении исходной утверждённой ревизии старый AnalysisSnapshot остаётся исторически идентифицируемым; текущий пересчитывается.
- Риск-сигналы не должны выдавать необоснованные бинарные решения «надёжный / ненадёжный» без раскрытия метода и ограничений.

## 6. React & visual acceptance

**Тестируемые страницы:** Project Setup, Statements, Excel Import Preview, React Financial Editor, Validation Workbench, Strategy Builder, Analytics Dashboard, Report Builder.

**Проверка UX:**
- Кнопка скачивания Excel расположена **под каждым отчётом** и скачивает только выбранную форму.
- После заполнения/загрузки доступны ошибки по строкам и ячейкам без просмотра логов разработчика.
- Обработка блокирующей ошибки не меняет уже согласованные цифры.
- Графики имеют русские подписи, годы, единицы (₸/тыс. ₸/млн ₸), текстовые пояснения, hover tooltip, легенды и табличную альтернативу.
- Нет сломанной вёрстки на desktop 1440×900, laptop 1280×800, планшете 768×1024.
- Контраст и состояние ошибки не выражены только цветом; управление с клавиатуры.
- Не показываются красивые, но математически бессмысленные круговые/потоковые диаграммы при неподходящих данных.

**Visual regression:** скриншоты ключевых страниц на светлой/тёмной теме и типовых размерах; изменения принимаются только после ревью.

## 7. Cross-format consistency

Для эталонного набора:
1. Заполнить Excel → импортировать → approve.
2. Заполнить те же значения через React → получить идентичный canonical fingerprint.
3. Вычислить индикаторы/правила → получить идентичные точные значения.
4. Экспортировать PDF/HTML/XLSX → сравнить числа, годы, единицы, версии, предупреждения и наличие разделов.
5. Сохранить .fin.json → переоткрыть → повторить расчёт → проверить полную эквивалентность результатов.

Снимок отчёта должен хранить версию методики. Если в приложении формула обновлена, старый анализ нельзя тихо объявить рассчитанным по новой версии.

## 8. Offline / privacy / resilience

- Закешировать необходимые статические ресурсы и открыть приложение без сети.
- Прогнать имитацию отсутствия сети при импорте, расчёте, визуализации, сохранении и локальном экспорте; функционал не должен обращаться к API.
- Проверить отсутствие сторонних запросов и передачи финансовых значений средствами сетевого логирования в E2E.
- Обновление страницы до сохранения локального проекта сопровождается предупреждением о риске потери данных (там, где браузер это допускает).
- Импорт повреждённого .fin.json и XLSX не вызывает падения всего приложения.
- Стресс-тесты: большие книги, множество периодов, частые переключения стратегий, длительная работа в одной вкладке.

## 9. Пайплайн CI (целевой)

~~~text
npm ci
npm run lint
npm run typecheck
npm run test:unit -- --coverage
npm run build
npm run test:e2e
npm run test:security-fixtures
~~~

Скрипты — контракт для будущей реализации, они **ещё не существуют**.

Тестовое покрытие: 100% обязательных бизнес-инвариантов и всех ветвей финансовых формул в тестовой матрице; количественные пороги line coverage вторичны. Не подменять бухгалтерскую правильность зелёным snapshot-тестом.

Отдельный S2 Review для: Excel протокола, финансовых формул, DSL стратегий и экспортной воспроизводимости.

## 10. Release Definition of Done

- Все бизнес-сценарии E2E-01…E2E-10 из FIN-SPEC имеют реальные успешные прогоны.
- Все blocker-проверки не позволяют утвердить недостоверные данные.
- Каждая формула воспроизводится на эталонных исходных значениях.
- При отсутствии данных нет скрытых нулей/подмены значений.
- После перезапуска восстановлен полный FIN-проект.
- В печатном отчёте нет расхождений с интерактивным Dashboard.
- Проверены браузеры Chromium, Firefox и WebKit на типовых данных.
- Для офлайн-режима нет обязательных сетевых запросов и серверного состояния.
- Нет критичных уязвимостей импорта/экспорта.
- В README указан проверенный способ запуска/сборки и известные ограничения.
- Документированы реальные команды тестирования, числа PASS/FAIL и неизменяемый commit SHA.

## 11. Первый исполняемый вертикальный срез

**FIN-R0+R1A / Balance Sheet 2024–2025** — приоритет номер один.

Требование: открыть React → создать компанию → скачать FIN Balance XLSX → заполнить значения за два года → загрузить → увидеть ошибку баланса → исправить → подтвердить → увидеть Current Ratio и тренд активов → сохранить .fin.json → восстановить проект.

Это самый короткий путь доказать одновременно корректность Excel, модели данных, проверок и пользовательской ценности FIN.

Прежде чем расширять шаблоны до всех отчётов, получить **реальный PASS** по этому сценарию. Следующие формы создаются на том же каталоге метрик и протоколе, а не дублируют код.

## 12. Release notes vs факты

Статусы обязательны:
- **PLANNED:** только требования.
- **IMPLEMENTED / UNVERIFIED:** код существует, полной доказательной базы нет.
- **TESTED:** показан реальный результат автотестов.
- **UAT PASS:** проверен ручной пользовательский сценарий.
- **RELEASE READY:** пройдены все gates и согласованы ограничения.

В момент создания этих документов **все этапы FIN-R0…R7 — PLANNED**.
